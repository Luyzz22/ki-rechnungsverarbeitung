### Records to create at STRATO

Two records, nothing else:

```
Type   Name         Value              TTL
A      industrie    207.154.200.239    3600
A      legal        207.154.200.239    3600
```

`A` rather than `CNAME`, to match how `app` is already configured. A CNAME would
also work but would introduce a second pattern in the same zone for no benefit.

**Do not touch** MX, SPF, DKIM, DMARC, any other mail record, or any existing
subdomain. The new records are additive; nothing existing is modified.

## TLS

The server already uses Let's Encrypt via certbot for `sbsdeutschland.com`.
`infra/scripts/issue-certs.sh` **expands** that certificate rather than issuing a
second one, so renewal stays a single job:

```bash
infra/scripts/issue-certs.sh
```

The script refuses to run until both new hostnames resolve, then runs
`certbot --nginx --expand` for all four names and finishes with
`certbot renew --dry-run`.

Verification:

```bash
curl -I https://industrie.sbsdeutschland.com
curl -I https://legal.sbsdeutschland.com
```

There are no mixed-content risks: the pages load no remote scripts, no remote
stylesheets and no remote fonts. `next/font` self-hosts Inter and IBM Plex Mono
at build time.

## Application-level routing

`src/proxy.ts` maps hostname to content. One page, one public URL.

```
Host                              Request              Action
industrie.sbsdeutschland.com      /produkte/normpilot  rewrite → /industrie/produkte/normpilot
industrie.sbsdeutschland.com      /industrie/…         308 → /…
legal.sbsdeutschland.com          /produkte/kanzleiai  rewrite → /legal/produkte/kanzleiai
legal.sbsdeutschland.com          /legal/…             308 → /…
sbsdeutschland.com                /industrie/…         308 → https://industrie.sbsdeutschland.com/…
sbsdeutschland.com                /legal/…             308 → https://legal.sbsdeutschland.com/…
anything else (localhost, …)      any                  pass through unchanged
```

The pass-through for unknown hosts is what keeps the whole ecosystem testable at
`http://127.0.0.1:3100` using the internal prefixes, without weakening the
production URL space.

nginx must forward the original `Host` header — `infra/nginx/snippets/sbs-web-proxy.conf`
sets `proxy_set_header Host $host`. If that line is removed the application sees
the upstream address and serves the corporate site on every hostname.

## Canonicals and sitemaps

Each hostname advertises only its own URLs:

```
sbsdeutschland.com/sitemap.xml              11 corporate URLs
industrie.sbsdeutschland.com/sitemap.xml    11 industry URLs
legal.sbsdeutschland.com/sitemap.xml        11 legal URLs
```

`sitemap.ts` and `robots.ts` read the `Host` header and emit the matching set,
so there is no cross-host duplication for a crawler to resolve. Canonical tags
are generated by `pageMetadata()` from the same `publicUrl()` function the
sitemap uses, which is why they always agree.

Verified in a browser with the three hostnames mapped to the local build:

```
https://sbsdeutschland.com/                            canonical https://sbsdeutschland.com
https://industrie.sbsdeutschland.com/produkte/normpilot canonical https://industrie.sbsdeutschland.com/produkte/normpilot
https://legal.sbsdeutschland.com/                       canonical https://legal.sbsdeutschland.com
https://industrie.sbsdeutschland.com/governance         404  (legal-only route, correctly isolated)
```

## www

`www.sbsdeutschland.com` is served by the same server block as the apex and
renders identical content, with canonicals pointing at the apex. If a permanent
redirect to the apex is preferred, add it to the corporate server block:

```nginx
if ($host = www.sbsdeutschland.com) { return 301 https://sbsdeutschland.com$request_uri; }
```

This is left out by default because the existing site currently answers on both
and a redirect is a behaviour change that should be a deliberate decision.
